# テスト

検出処理（`lib/autoCrop.js`）を変更したら、**デプロイ前に必ず全部を通すこと**。
一部だけでは不十分で、実際にそれで失敗している（下の「経緯」を参照）。

```bash
npm install
npm test            # 4つ全部
npm run test:orientation   # 向き判定だけ（写真がなくても走る）
```

## 準備

`test:orientation` 以外は個人の写真が要る。

```bash
export TEST_DIR=./test/data         # 画像を置く場所
export CHROME_PATH=/path/to/chrome  # 省略時は playwright の既定を使う
```

`playwright-core` に同梱の Chromium とビルド番号がずれている環境では、
`CHROME_PATH` を明示しないと起動できない。入っているものを探すには:

```bash
ls -d "${PLAYWRIGHT_BROWSERS_PATH:-$HOME/.cache/ms-playwright}"/chromium-*/chrome-linux/chrome
```

`$TEST_DIR` に以下を置く（個人の写真なのでリポジトリには含めない）。

| ファイル | 内容 |
|---|---|
| `final.jpg` | 正しく切り出せた画面画像。合成テストの素材に使う |
| `IMG_6407.jpeg` | 実写真1: 暗い机、画面が大きめに写っている |
| `IMG_6681.jpeg` | 実写真2: 明るい木の机、画面が小さめ、本体に赤いシール |
| `IMG_6682.jpeg` | 実写真3: 斜めに置いた状態。ガラスに光の反射が入っている |
| `IMG_6706.jpeg` | 実写真4: 白い机の上のホーム画面。机の方が画面より明るい |

## 1. 向き判定テスト（写真不要）

```bash
node test/orientation.mjs lib/autoCrop.js
```

画面らしい絵をその場で描いて `autoOrient` にかける。個人の写真が要らないので、
どの環境でもそのまま走る。

考え方は「正立した画面を k 度回した画像を入れたら、`autoOrient` は k を
打ち消す回転を返さなければならない」（`(k + rotation) % 360 === 0`）。
k=90/270 は、横向きで撮った写真に対応する。

条件は 3種類の画面（バーコード画面／ホーム画面／明るいリスト画面）×
3種類の切り出し範囲 × 4方向の 36通り。切り出し範囲は、向き判定の手掛かりが
どこまで残っているかを変えるためのもの:

| 範囲 | 内容 |
|---|---|
| `none` | 表示面ぴったり（理想の切り出し） |
| `bezel` | 表示面＋本体の黒い枠。iPhone はホームボタン側のほうが広い |
| `case` | さらに明るい色のケースの縁まで（検出が本体の外周を拾った状態） |

合格の目安: **36/36**。1つでも落ちたら向き判定の回帰。

## 2. 合成テスト（正解が分かる）

```bash
node test/synthetic.mjs lib/autoCrop.js
```

`final.jpg` を既知の回転角・遠近・大きさで「机の上のスマホ写真」に変換し、
検出結果を正解と比べる。14条件（正面／回転／遠近／小さく写る／暗い背景／
隣に白い紙／本体にシール）。

合格の目安: **角度誤差 最大 0.3度以内**、平均のずれ 50px 以内。

## 3. 実写真テスト（正解は無いが、性質で判断できる）

```bash
node test/photos.mjs lib/autoCrop.js タグ名
```

出力される指標:

| 指標 | 意味 | 目安 |
|---|---|---|
| 縦横比 | 切り出し結果の縦横比。この端末の表示面は 1.779 | 1.72〜1.80 |
| 上の傾き / 下の傾き | 画面上部・下部にある水平線の傾き | ±0.2度以内 |
| 縦線 | カードの左端など、垂直であるべき線の傾き | ±0.3度以内 |
| ベゼル左右 | 左右に本体の黒い枠が写り込んでいる幅（％） | 3%以内 |

`$TEST_DIR/タグ名_6407_overlay.jpg` などに、検出した四隅を重ねた画像と
切り出し結果が保存される。**数値だけでなく必ず目で確認すること。**

## 4. 環境差テスト

```bash
node test/robustness.mjs lib/autoCrop.js
```

明るさ・ガンマを変えた画像でも、上下の向きの判定が変わらないことを確かめる。
端末やブラウザによって写真の色の出方（色プロファイルの扱い）が違うため、
絶対的な輝度値で判断していると結果が変わってしまう。全条件で同じ向きになること。

## 5. 1枚だけ詳しく調べる（テストではない）

```bash
node test/diag.mjs lib/autoCrop.js IMG_7003
```

うまくいかない写真が出てきたときの切り分け用。どちらの経路が動いたか
（本体検出の有無）、四隅、四隅の縦横比、向き判定の各分岐の値
（黒帯の幅・端の彩度・端の明るさ）を出し、overlay と結果の画像を書き出す。

**症状から原因を推測しないこと。** 直近の失敗でも、最初に立てた仮説
（黒い壁紙が黒帯の判定を誤爆させている／本体経路が動いている）は
2つとも外れており、このスクリプトを回して初めて本当の原因
（ケースの縁が画面と一緒にまとめられていた）が分かった。

## 「写真を選択」が開かないとき（まず端末を疑う）

**コードより先に、ブラウザを変えて試すこと。** Safari で開くなら、アプリの
不具合ではない。

- Safari では開く → Chrome for iOS の写真アクセス許可。
  設定 → アプリ → Chrome → 写真 →「すべての写真」で直る
- どのブラウザでも開かない → スクリーンタイムの制限か iOS 側の不具合

v1.14.1 でこれを間違えた。「タップしても開かない」という報告に対し、
ファイル入力の `display:none` が原因だと判断してコードを直したが、実際の原因は
Chrome の写真アクセス許可だった（Safari では同じ版が正常に動いていた）。
`display:none` をやめた変更自体は iOS 向けの定石なので残してあるが、
**あの報告を直したのはコードではない。**

同じ日に、切り出しの不具合（v1.14.0）でも症状からの推測を2回外している。
このリポジトリでは、**症状から原因を推測しない**こと。切り分けの材料を先に取る。

## 6. 写真の選択が開くか（アプリを動かして確かめる）

```bash
npm run build && npx next start -p 3111
APP_URL=http://localhost:3111 node test/filepicker.mjs
```

「写真を選択」をタップしたときに、写真の選択画面が開く作りになっているかを見る。

**このテストの限界を理解して使うこと。** iOS では `display:none` のファイル入力は
タップしても選択画面が開かないことがある（v1.14.1 で実際に起きた）。ところが
Chromium は `display:none` でも開いてしまうので、「タップで開いたか」だけでは
iOS の不具合を捕まえられない（手元で確認済み）。そこで、iOS で開くための
必要条件である「入力要素が実際に描画されていること」を主な判定にしている。
iOS の実機での動作そのものは保証できないので、最後は実機で試すこと。

## `final.jpg` について

合成テストの素材は「正しく切り出せた画面画像」であれば何でもよい。
手元に無い場合は、実写真から表示面だけを切り出して作れる。`test/diag.mjs`
で表示面の四隅を確かめ、`warpPerspective` で切り出して保存する。
**ベゼルを1pxも含めないこと**（合成テストの正解が狂う）。

## 経緯（同じ失敗を繰り返さないために）

- v1.4.0: 合成テスト12条件すべてで大幅に改善したが、実写真では
  下辺が本体のシールに引かれて四隅が崩れた（縦横比 2.015）。
  合成テストの「本体」がただの黒い四角で、実物とかけ離れていたため
  見抜けなかった。→ シールの条件を合成テストに追加した
- v1.5.0: 同じく合成テストのみで確認して出し、v1.4.0 の問題を引き継いだ
- v1.8.0: 実写真2枚と合成14条件の両方を通してから出したが、3枚目の写真
  （斜めに置いてガラスに反射が入ったもの）で四隅が崩れた。反射が画面と
  ひとつながりの明るい領域になり、四角形が引き伸ばされていた
- v1.9.0: 実写真3枚に増やして対応。RANSAC の乱数を固定の種にしたので、
  同じ写真からは必ず同じ結果になる（テスト結果が揺れない）
- v1.10.0: 左右がやや広く取られ、本体の黒い枠が写り込んでいた。画面と
  平行に走る「ケースの縁」を拾っていたため。明るい内容の外端より外へは
  ほとんど出さない制限を追加し、ベゼルの写り込みを指標に加えた
- v1.12.0: 白い机の上のホーム画面で、画面の一部しか取れず斜めに切れていた。
  「明るい領域＝画面」という前提が、机の方が明るい写真では成り立たない。
  本体（暗い塊）を先に検出して切り出す経路を追加した。この経路では
  ベゼルまで含めたガラス面が取れるため、縦横比は表示面より縦長になる
- v1.13.0: 向きの判定が絶対的な輝度値に依存していたのを、画像ごとの
  相対値で判断するように変更（環境差テストを追加）
- v1.14.0: 明るい色（水色）のケースを付けた端末で、ケースの外周まで
  切り出し、さらに上下が180度逆になっていた。ケースの縁が暗い机に対して
  「明るい領域」になり、画面の中身と一緒にまとめられていたのが原因。
  向きの誤りはその結果にすぎず、向き判定自体は無実だった（36条件の
  向き判定テストでは最後まで再現しなかった）。
  **症状から原因を推測して2回外した。** 実物を `test/diag.mjs` に
  かけるまで真因は分からなかった。次も同じ順序で進めること
