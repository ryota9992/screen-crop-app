## 1. 向き判定テスト（写真不要）

```bash
node test/orientation.mjs lib/autoCrop.js
```

画面らしい絵をその場で描いて `autoOrient` にかける。個人の写真が要らないので、
どの環境でもそのまま走る。

考え方は「正立した画面を k 度回した画像を入れたら、`autoOrient` は k を
打ち消す回転を返さなければならない」（`(k + rotation) % 360 === 0`）。
k=90/270 は、横向きで撮った写真に対応する。

条件は 3種類の画面（バーコード画面／ホーム画面／明るいリスト画面）×
3種類の切り出し範囲 × 4方向の 36通り。切り出し範囲は、向き判定の手掛かりが
どこまで残っているかを変えるためのもの:

| 範囲 | 内容 |
|---|---|
| `none` | 表示面ぴったり（理想の切り出し） |
| `bezel` | 表示面＋本体の黒い枠。iPhone はホームボタン側のほうが広い |
| `case` | さらに明るい色のケースの縁まで（検出が本体の外周を拾った状態） |

合格の目安: **36/36**。1つでも落ちたら向き判定の回帰。

## 「写真を選択」が開かないとき（まず端末を疑う）

**コードより先に、ブラウザを変えて試すこと。** Safari で開くなら、アプリの
不具合ではない。

- Safari では開く → アプリの不具合ではない。Safari を使う
- どのブラウザでも開かない → スクリーンタイムの制限か iOS 側の不具合

**Chrome for iOS で開かない事例があるが、原因は分かっていない。**
設定 → アプリ → Chrome → 写真 では直せない。Chrome は写真の「追加のみ」の許可
しか要求しないため、読み取りを許可する選択肢が出てこない（実機で確認済み）。
写真を選ばせるときは許可の要らないシステムの写真ピッカーが使われるので、
この設定は原因ではないと思われる。

この件では推測を2回続けて外した。

1. ファイル入力の `display:none` が原因だと判断してコードを直した（v1.14.1）。
   だが v1.13.0 でも同じ症状が出ており、コードとは無関係だった。
   `display:none` をやめた変更自体は iOS 向けの定石なので残してあるが、
   **あの報告を直したのはコードではない**
2. 次に Chrome の写真アクセス許可が原因だと判断し、「すべての写真」に変える
   よう案内した。だが実機にその選択肢は無く、手順自体が実行できなかった

同じ日に、切り出しの不具合（v1.14.0）でも症状からの推測を2回外している。
このリポジトリでは、**症状から原因を推測しない**こと。切り分けの材料を先に取る。
分からないときは「分からない」と書いて、回避策（Safari を使う）を示すこと。

## 6. 写真の選択が開くか（アプリを動かして確かめる）

```bash
npm run build && npx next start -p 3111
APP_URL=http://localhost:3111 node test/filepicker.mjs
```

「写真を選択」をタップしたときに、写真の選択画面が開く作りになっているかを見る。

**このテストの限界を理解して使うこと。** iOS では `display:none` のファイル入力は
タップしても選択画面が開かないことがある（v1.14.1 で実際に起きた）。ところが
Chromium は `display:none` でも開いてしまうので、「タップで開いたか」だけでは
iOS の不具合を捕まえられない（手元で確認済み）。そこで、iOS で開くための
必要条件である「入力要素が実際に描画されていること」を主な判定にしている。
iOS の実機での動作そのものは保証できないので、最後は実機で試すこと。

## 7. 撮り方の影響を測る（テストではない）

```bash
node test/shooting.mjs lib/autoCrop.js
```

机の明るさ・ケースの明るさ・傾き・画面の大きさ・画面の明るさを振って、
どの条件で誤差が跳ねるかを測る。撮影の指針を推測ではなく数字で決めるためのもの。

測定結果（v1.14.2 時点）:

| 要因 | 効くか | 境目 |
|---|---|---|
| ケースの明るさ | 最重要 | 明度140以下は誤差11px、150以上で127px |
| 明るいケース＋暗い机 | 最悪の組み合わせ | 机20でNG、机60以上ならOK |
| 画面の大きさ | 効く | 写真の幅の40%未満でNG（25%で70px） |
| 大きすぎ | 効く | 本体が写真の端に接すると破綻（1262px） |
| 画面の明るさ | 少し効く | 30%までOK、20%でNG |
| 遠近（傾き） | 効かない | 20%まで誤差は変わらない |
| 机の明るさ単体 | 効かない | 20〜240で差なし |

**「机を暗くすると良い」は誤り。** 効くのはケースの色であって机ではない。
むしろ明るいケースのときは、暗い机が最悪の条件になる。

合成なので実写真の代わりにはならない。ケースの件は実写真 IMG_7003 の失敗と
一致しているが、他は傾向として扱うこと。また IMG_7448 はこの推奨どおり
（黒ケース・明るめの机）で撮られていて、それでも失敗している。
撮り方で回避できない問題があることを忘れないこと。

## `final.jpg` について

合成テストの素材は「正しく切り出せた画面画像」であれば何でもよい。
手元に無い場合は、実写真から表示面だけを切り出して作れる。`test/diag.mjs`
で表示面の四隅を確かめ、`warpPerspective` で切り出して保存する。
**ベゼルを1pxも含めないこと**（合成テストの正解が狂う）。

## 未解決: 斜めから撮った写真で、上辺が最初からずれる（IMG_7448）

黒いケース・明るい机・少し斜めから撮った写真で、切り出しの上辺が
**部品から四角形を作る段階ですでに約8度ずれている**。

実測（1800x2400 換算）:

- 表示面の本当の上端: x460 で y295、x1360 で y269（ほぼ水平、-1.7度）
- `detectRoughQuad` が返す上辺: 495,341 → 1440,446（+6.7度）
- 左右と下の辺は実測値と一致している。**ずれているのは上辺だけ**

ステータスバーの連結成分自体は正しく取れている（bbox は表示面の上端に届いて
いる）。にもかかわらず `largestQuad`（凸包から面積最大の四角形を選ぶ）が
上辺を拾いきれていない。ステータスバーは水色で輝度が低め（平均156、カードは
225）なので二値化の縁がぎざぎざになり、凸包の頂点が上端に乗らないためと
思われるが、**確かめていない**。

v1.14.2 で `OUTSIDE_MARGIN` を 0.5%→2% にして緩和した。ステータスバーは
ほぼ入るようになったが、上辺の傾き自体は残っている（上端が斜めに欠ける）。
根本的には `largestQuad` の作り直しが要る。

やってはいけないこと（試して悪化を確認済み）:

- **内側再探索の結果が内容を切り落とすなら不採用にする**: 上辺の傾きが
  0.22度→5.70度に悪化した。内側再探索は、内容を削る代わりに幾何的には
  まっすぐな四角形を作っていた
- **`OUTSIDE_MARGIN` を 4%以上にする**: 左のベゼル写り込みが 0.6%→1.8%
  （4%）、3.9%（6%）に増える。v1.10.0 で潰した問題が戻る
